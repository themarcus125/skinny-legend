# Cloudflare R2 — photo bucket (SKI-39)

R2 stores every binary the app produces: originals, thumbnails, avatars, feedback screenshots.
The API never proxies uploads; it hands the iOS app a **presigned PUT** (`POST /uploads/presign`,
5-minute TTL) and the app uploads straight to R2. Reads go back out as presigned GET URLs
(1-hour TTL) that the API embeds as `photoUrl` / `thumbUrl` / `avatarUrl`.

## 1. Create the bucket

Cloudflare dashboard → **R2** → **Create bucket**.

- Name: **`skinny-legend`** (this is `R2_BUCKET`'s default in `apps/api/src/env.ts`; any other
  name must be set explicitly on Railway).
- Location: automatic, or a hint near the members (APAC).
- **Public access: off.** Nothing here is world-readable; every read is a signed URL.

Key layout written by `apps/api/src/services/storage.ts`:
`photos/<userId>/<uuid>.jpg`, `thumbs/…`, `avatars/…`, `feedback/…`.

## 2. API token, scoped to this bucket only

R2 → **Manage API Tokens** → **Create API Token**.

- Token name: `skinny-legend-api`
- Permissions: **Object Read & Write** (not Admin Read & Write — the API never creates or
  deletes buckets).
- Specify bucket: **Apply to specific buckets only → `skinny-legend`**.
- TTL: forever (or set a rotation reminder).

Cloudflare then shows, once:

| Shown as | Paste into Railway as |
| --- | --- |
| Access Key ID | `R2_ACCESS_KEY_ID` |
| Secret Access Key | `R2_SECRET_ACCESS_KEY` |
| Account ID (top of the R2 page / in the S3 endpoint URL) | `R2_ACCOUNT_ID` |
| bucket name | `R2_BUCKET` (`skinny-legend`; optional, that is the default) |

The endpoint is derived, not configured: `https://<R2_ACCOUNT_ID>.r2.cloudflarestorage.com`
with `region: 'auto'`.

These four values are **secrets** — they go into Railway's Variables tab (API, `cleanup` and
`notify` services all need them; `cleanup` lists and deletes objects), never into the repo and
never into chat.

## 3. CORS

R2 → bucket `skinny-legend` → **Settings → CORS policy → Add CORS policy**, paste:

```json
[
  {
    "AllowedOrigins": ["*"],
    "AllowedMethods": ["PUT", "GET", "HEAD"],
    "AllowedHeaders": ["content-type"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 3600
  }
]
```

Why `*`:

- The uploader is the **iOS app**, and a native `URLSession` request has no `Origin` header and
  is not subject to CORS at all. There is no origin to allow-list. The entry that matters is
  therefore a defensive one for any browser-side uploader (a future web client, or curl-from-
  devtools during debugging).
- The guard on a PUT is **the presign signature, not the origin**. The URL is signed for one
  exact key, one exact `Content-Type` (`apps/api/src/routes/uploads.ts` only signs
  `image/jpeg`, `image/png`, `image/heic`), and expires after 5 minutes; the bucket itself is
  private. An `Origin: *` allowance grants a browser nothing it could not already do with the
  same signed URL from a non-browser client. `AllowedHeaders: ["content-type"]` is what makes
  the browser preflight for a PUT succeed, since the signature covers that header.
- `ETag` is exposed so a browser uploader can read the upload's ETag; harmless otherwise.

### Do I need the admin origin for GET?

Not today. The admin renders photos with plain `<img src={entry.thumbUrl}>`
(`apps/admin/src/components/entries/entries-table.tsx`, `override-dialog.tsx`,
`components/map/entry-map.tsx`) and a plain image load is not a CORS request — the signed GET
URL works with no CORS policy at all.

Add the admin origin only if the dashboard ever `fetch()`es an object, draws one into a
`<canvas>`, or sets `crossorigin` on an image. In that case append a second rule rather than
widening the first:

```json
  {
    "AllowedOrigins": ["https://<admin-domain>.vercel.app", "http://localhost:3001"],
    "AllowedMethods": ["GET", "HEAD"],
    "AllowedHeaders": ["*"],
    "MaxAgeSeconds": 3600
  }
```

## 4. Verify

With the four variables set on Railway and an admin session:

1. Call `POST /uploads/presign` with `{"kind":"photo","contentType":"image/jpeg"}` and a valid
   Bearer token — you get `{ key, url, expiresAt }`.
2. `curl -X PUT -H 'Content-Type: image/jpeg' --data-binary @photo.jpg '<url>'` → `200`.
3. The object appears under `photos/<userId>/…` in the bucket.

A `403 SignatureDoesNotMatch` on step 2 almost always means the `Content-Type` sent differs
from the one presigned.

## 5. Lifecycle

Do **not** add an R2 lifecycle rule that expires objects: confirmed entries keep their photos
for the whole challenge. Orphan collection is the `cleanup` cron
(`apps/api/src/jobs/cleanup.ts`, Mondays 03:00 UTC), which deletes only objects older than 24 h
that no database row references.
